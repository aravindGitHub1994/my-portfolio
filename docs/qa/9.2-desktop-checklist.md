## 0 · Setup (do this first)

The site is a static export, so `npm start` will **not** serve it correctly.
Build it and serve the `out/` folder:

```bash
npm run build
npx serve out -l 3005      # → http://localhost:3005
```

**Reset your browser state before the first-run test.** Three keys persist and
will silently skip or alter what you're testing. In DevTools → Console:

```js
localStorage.removeItem("w98-intro-seen");     // skips the power-on intro
localStorage.removeItem("w98-muted");          // remembers your mute choice
localStorage.removeItem("w98-fidelity-floor"); // remembers an accepted downgrade
location.reload();
```

**Two things are stripped from production builds** and cannot be used here:
`window.__fidelity` and the on-screen perf counter. They exist only on
`npm run dev`. Where a step needs them, it says so.

**Pacing note:** the full journey needs the power button *clicked* and roughly
15 seconds of boot before scrolling moves anything.

## 17 · Session 13 — the two blocking fixes

### 17a · Docking sensitivity (§3, §4)

Two separate defects, found in that order:

1. **The dock could be scrolled past.** Engagement was a proximity test only
   — `|progress − rest| < 0.004`, about 25 px of a 5040 px runway, sampled
   once per rAF. A wheel flick covers more than that between frames, so the
   band was jumped clean over. It now also tests for *crossing* the rest
   point in either direction, with a wider band (0.012, re-arm 0.05). On
   latch, scroll stops and Lenis glides the last of the way to the exact
   square-on pose over 0.3 s before the DOM cross-fades, so the shell can
   never land over a mis-posed CRT.
2. **Chapter 4's Lenis snap was removed.** That soft snap and the dock were
   two mechanisms competing for one landing — the "really sensitive" feel —
   and it was what tugged the visitor back after an undock. Chapters 1, 2, 3
   and 5 keep their snaps untouched.
3. **The dock was being ejected by the visitor's own momentum.** With (1)
   fixed, the dock latched correctly and was then undocked ~1.7 s later by
   the tail of the same flick — every leftover wheel event read as undock
   intent, and the desktop flashed past. Nothing undocks for 800 ms after
   the latch now, and after that an undock must follow a 350 ms pause in
   scrolling. Auto-repeat keydowns are ignored for the same reason.

### 17b · Scroll cue (§15)

The static floor's mark (label + hairline with a light pulse, from
`acts/Hero.tsx`) reused on the journey. Fades in after ~2 s of stillness at
any rest point; fades out on the first scroll. Hidden while docked, during
boot, on the BSOD, and at the end of the ride. Pointer-inert and
`aria-hidden`.

**Corrected 2026-07-28 (plan-0010 §7.2 — record was wrong, code was right).**
This section said the cue "fades in ~0.9 s after the desktop settles". It
does not, and never did. `START_STALL_MS` is 900 ms, but `stillSince` is
initialised at component mount and the boot sequence never moves
`scrollProgress`, so that window has long since elapsed by the time
`win98State.phase` reaches `"desktop"`. The cue therefore begins ramping on
the **first `"desktop"` frame**. Harmless — the phase gate is what was
actually keeping it off the boot — but the two should not disagree.

**Amended 2026-07-28 (plan-0010 §7.1).** The cue is the same mark but no
longer the same values: the journey instance now carries a scrim, a rail at
48 % rather than `--color-line`'s 12 %, `--color-ink` with a shadow instead
of `--color-ink-subtle`, `--color-accent-bright` in the pulse, and its own
`scroll-cue-journey` keyframes (linear, parked 20 % of the cycle rather
than the floor's ~40 %). The fade is a linear ramp that reaches full in
`FADE_MS`; the old exponential ease asymptoted and never arrived. The
gating logic is byte-for-byte unchanged, and `acts/Hero.tsx` still uses the
original tokens and keyframes against the floor's flat `--color-bg`.

**Owner-confirmed 2026-07-28** on the dev server: the cue reads. P7 closed.

Verified in an isolated headless session at 1440×900: legible over the
chapter-1 desktop close-up (the bright backdrop that caused the defect) and
over the chapter-3 and chapter-5 dusk shots, where the scrim does no visible
work; opacity 0 while docked and past `END_P`; `acts/Hero.tsx` untouched.

**Newly exposed, owner's call — not fixed here.** Now that the cue is
actually visible, it is visible *underneath the SignOff card*: at p ≈ 0.94
the "Scroll" label sits roughly 30 px below the contact links and competes
with them. This is not a regression — the cue has always run to `END_P`
(0.995) and SignOff has always started at `REST_POINTS[4]`; the overlap was
simply invisible before. Fixing it means changing the gate, which ADR-013
§10 explicitly puts out of scope for this pass ("contrast, not new logic").
The options if the owner wants it closed: drop `END_P` to just under
SignOff's start, or add a SignOff term to `wanted`.
